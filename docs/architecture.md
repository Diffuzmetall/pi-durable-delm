# Как устроен DeLM для Pi Durable 1.4

## Текущая интеграция

DeLM — доска, переносимый скилл, launcher и расширение существующего Native. Он не поставляет собственный Durable, Harness или замену хранилища.

| Часть | Текущий механизм |
|---|---|
| Доска и CLI | Python, задачи и события в двух собственных SQLite-базах |
| Native | Уже установленный Pi Durable 1.4, его registry и штатный владелец беседы |
| Расширение | `extensions/delm/native14.js` и `native14-owner.js`, SDK Durable/AI/Chord 1.4.0 |
| Принятие ввода | Подлинный выбранный admission controller; исходный тип, текст, SHA и стабильный request ID |
| Управление | Приватный Unix socket внутри того же Native-процесса; точные actor/run/workspace/session/instance |
| Launcher | `prepare → serve → open` каждого участника `→ start`; отдельные обычные терминалы |
| Просмотр | Тот же `DeLM BOARD`, режим `--observe`, без записи и ACK за участника |

Доска хранит состояние задач; Native исполняет беседы, инструменты и ожидания. Приватный socket не создаёт второй сервер исполнения и не обходит guards. Мультиплексор терминалов, публичный host patch и старый session-facet API для этого пути не нужны.

Подробности: [текущий контракт](native14-contract.md), [эксплуатация](native14-operations.md), [настройка агентом](agent-setup.md), [локальная установленная приёмка](native14-acceptance.md) и [итоговый индекс с поправкой измерения](../evidence/native14/acceptance/final-review-index.json). Приёмка проверяет конкретную установленную сборку и SDK 1.4.0, не любую программу с похожим номером версии. Живая команда не перезагружалась; качество живой модели не проверялось.

## Историческая архитектура public Native 1.0.2

Ниже сохранено описание прежнего проверенного варианта с session facet и отдельной API-поправкой. Это история и объяснение общих принципов доски, **не инструкция подключения текущего Native 1.4**. Упоминания прежних API, клиента и 39 HTTP-запросов относятся только к этому варианту.

DeLM помогает участникам работать над одним результатом в общей папке. Доска хранит задачи и полезные сообщения; каждый участник сохраняет собственную беседу Native. Скилл готовит запуск, но не становится постоянным пятым агентом-руководителем.

```text
Запрос пользователя → согласованный план
                              ↓
                       2 / 4 / 8 участников
                         ↕   ↕   ↕
                         общая доска
                         ↕   ↕   ↕
                     одна папка проекта
                              ↓
                    проверенный общий результат
```

## Разделение ответственности

| Часть | Что делает | Чего не делает |
|---|---|---|
| Python-доска | Задачи, зависимости, события, публикации, чтения, бронь | Не исполняет модели и не владеет беседами Native |
| Native session facet | Расширяет существующий registry; exact/work и доставка в ту же беседу | Не создаёт host/Harness, не назначает задачи, не пишет Native SQL |
| Скилл и launcher | Подготовка плана, команды, стартовых инструкций, точное продолжение | Не создают разрешение на запуск моделей |
| Observer | Таблица, история, поиск, детали | Не подтверждает чтение за участника |
| Пользователь | Цель, ограничения, разрешённые расходы и публикация | Не обязан вручную переносить ответы между участниками |

## Граница с существующим Native

Host принадлежит пользователю: его loader, registry, conversation, scheduler, guards, модели и SQLite уже существуют. Session facet через локальный `DurableSession` API 1 получает ссылки на **эти же** объекты, а не создаёт второго владельца. Удалённый RPC доступ к этой capability запрещён самим сервером, не только флагом клиента. Короткоживущий публичный клиент подключается к точному Unix socket; код host не включён в пакет и не импортируется launcher по личному пути.

Собственный `delm.control` связывает actor/run с точными session path, workspace, conversation и persistent instance ID. Текст, тип, request ID и его SHA сохраняются перед штатным `Conversation.submit`; изменённый payload под старым ID не становится новым разрешённым вводом. Дополнительная реальная owner policy остаётся обязательной, если host её имеет. Native tool guards сохраняются; никакой «разрешающей» admission-заглушки в product flow нет.

Проверен публичный Native v1.0.2 с отдельной минимальной API-поправкой трёх файлов. Это условие совместимости, **не stock Native и не поставка fork/framework**. Копии публичного source использовались только как внешние disposable test fixtures. Обычный Pi 1.4 и Pocket не заменяют этот Native. [Точный контракт](native-compatibility.md).

Session facet и скилл обнаруживаются разными механизмами. Facet загружает штатный Chord loader; скилл — штатный Native `loadSkills` через project-local `.pi/skills/delm`. Проверка имени и location в настоящем model prompt не заменяется полем `pi.skills`. [Подключение](operations.md#подключить-к-существующему-native).

## Файлы и данные

```text
Установленный пакет/
  scripts/                  Python-доска, CLI и observer
  vendor/DeLM/              закреплённый upstream с лицензией
  extensions/delm/          Native-компонент
  skills/delm/              переносимый скилл и launcher
  prompts/                  шаблон worker-контракта
  examples/                 небольшие примеры
  tests/                    проверка поставки

Проект пользователя/
  AGENTS.md                 правила проекта
  исходники и результат      одна общая рабочая папка

Приватный RUN вне проекта/
  context.sqlite            задачи, события, receipts, leases
  context-bodies.sqlite     тела вложений исходного DeLM
  WORKER.md                 зафиксированный контракт запуска
  ACTOR/START.md            личность и пути конкретного участника
  ACTOR/bin/context         CLI с привязкой к этому участнику
  launch.json               точные сессии и состояние стартовой доставки
  config.json               служебная привязка с секретами; не публиковать
  server.log                журнал backend

Хранилище Native/
  отдельные session.sqlite  беседы, scheduler и принятые входы
```

Одна логическая доска не означает один физический файл. При backup нужны обе базы доски; сохранение только `context.sqlite` может потерять вложения. Native state сохраняют штатными средствами Native, не открывая живую session вторым владельцем.

`launch.json` не дублирует задачи. Старое окно, PID или запись endpoint не доказывают, что сервис работает сейчас. При продолжении выбирают точную session: общий `--continue` для нескольких участников одного cwd недопустим.

## Как делится работа

Участник читает правила, утверждённый план и свежую доску. Он выбирает полезный доступный результат, выигрывает атомарный claim и пишет только в согласованных пределах. Одновременно можно удерживать одну незавершённую задачу.

Ранний результат лучше оформить отдельной выходной задачей. Например, готовый контракт данных позволяет другим начать API и интерфейс, пока автор продолжает реализацию. DONE такого контракта не завершает его родителя или всю работу автора.

- **2 участника:** небольшой объём действительно независимой работы.
- **4 участника:** четыре полезных направления с непересекающимися областями записи.
- **8 участников:** восемь таких направлений, отдельное разрешение и достаточные ресурсы. Восемь fixture identities не доказывают работу восьми живых LLM.

## Смысл ожиданий, ошибок и брони

**Exact wait:** нужен конкретный результат; готовы должны быть все названные UUID. Связанный FAIL или завершившийся производитель могут разбудить для разбора, но это не READY.

**Work wait:** свободный участник ждёт доступную работу. Пробуждение лишь подсказывает возможность: задачу всё равно нужно прочитать и захватить. Конкурент может успеть первым; справедливое распределение не гарантируется.

**Связанный FAIL:** мешает закрыть затронутый результат и продвинуть зависимые задачи, но не останавливает независимую работу. Историю не удаляют; исправление явно ссылается на ID ошибки.

**Advisory lease:** проверяемая доской договорённость о путях и ресурсах, не OS-lock. Произвольный shell-процесс способен записать файл вопреки ей. TTL не доказывает смерть процесса.

## Что переиспользовано

Закреплённый Python DeLM предоставляет события, ProtectedBoard, HTTP handler и CLI. Наш слой добавляет зависимости, защиту от старых команд, snapshots/read/ACK, leases, observer и Native-продолжение. Это не официальный продукт авторов исследования и не Rust runtime отдельного продуктового плагина.
