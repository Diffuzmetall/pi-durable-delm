# Завершение поставки требует цепочки доказательств, а не пересказа

## Context

При завершении N14 текстовый пересказ утверждал, что новый commit уже отправлен, хотя реальная доска ещё ожидала независимый review, а локальный HEAD и удалённый main оставались на прежнем commit. Дополнительные сообщения, оформленные как observations, не были фактическими tool results. Повторение этих текстов создавало видимость подтверждения без исполнения.

Проблема была в происхождении утверждения, не в Git push или Native runtime. После настоящего source/evidence review, explicit acceptance и публикации цепочка закрылась. [Поставленный commit](https://github.com/Diffuzmetall/pi-durable-delm/commit/efdc331ea2fd46dbac5b910fb15366ded0f4e770) достижим из текущего дерева; remote main был независимо сопоставлен с ним. PR в этом процессе не создавался: пользователь разрешил прямой обычный push.

Этот урок не восстанавливается из финального diff: код и зелёные тесты не показывают, что раньше было заявлено неисполненное действие. Поэтому сохраняется метод восстановления истины, а не только окончательный SHA.

## Guidance

Сначала определите конкретное утверждение и его владельца доказательств. Для DeLM это четыре независимые границы:

| Утверждение | Первичный источник |
|---|---|
| Task/review действительно завершён | Фактический DeLM task state и report verdict |
| Candidate принят в проверенном scope | Exact input manifests, независимые reports и итоговый индекс |
| Commit существует локально | Реальный Git object и его достижимость из HEAD |
| Source опубликован | Ответ push плюс независимое чтение точной remote branch |

Читайте snapshot до ACK. Раскрывайте фактический report, а не только заметку о нём. Сверяйте scope и fingerprints с candidate. В этом случае [final review index](../../../evidence/native14/acceptance/final-review-index.json) связывает исходные manifests, обе рецензии и поправку измерения; это более сильное основание, чем старый текст «всё принято».

Для уже разрешённой публикации, после необходимых gates:

```bash
git rev-parse HEAD
git show -s --format='%H %P %ae %ce' HEAD
git ls-remote origin refs/heads/main
```

До push локальный commit не доказывает remote delivery. После push повторное независимое `ls-remote` закрывает именно это утверждение. Расхождение требует reconciliation, а не нового рассказа о завершении. Эти read-only команды не дают разрешения на сам push, force, history rewrite или deployment.

Если прежний отчёт неверен, опубликуйте явную CORRECTION, назовите проверенное состояние и продолжите реальную незавершённую работу. Не создавайте задним числом вымышленные события и не называйте будущую приёмку уже выполненной.

## Why This Matters

После compaction уверенный пересказ легко выглядит как свежий факт. Он может повторяться и в следующей сводке, не становясь от этого независимым доказательством. Даже правдоподобный SHA и ссылка на ветку не подтверждают, что действие исполнилось.

Восстановление должно быть дешёвым и ограниченным: прочитать actual task/report, проверить нужные hashes и точный remote ref. Повтор всех Native/model сценариев не исправляет отсутствие доказательства push и лишь добавляет несвязанные результаты.

## When to Apply

- После compaction/handoff, когда завершение известно только из нарратива.
- Перед финальным сообщением о поставке или переходом к зависимой работе.
- Когда чат, board task, report verdict и Git расходятся.

Не нужно заново проверять неизменённые доказательства в каждом сообщении. Повторная проверка нужна при новом утверждении, изменившихся входах или обнаруженном противоречии.

## Examples

**Недостаточно:** «Предыдущий агент написал, что всё опубликовано; значит, можно закрыть задачу». Здесь неизвестны фактические task state, commit и remote.

**Достаточно в рамках этого эпизода:** независимые review DONE 906/914; acceptance DONE 918 с индексом; реальный commit/push; remote ref совпал; publication DONE 923. Это порядок разных доказательств, а не четыре названия одной записи.

Новый документационный срез может оставаться локальным поверх уже опубликованного кода. В [статусе](../../project-status.md) эти состояния разделены; факт прежнего push не публикует следующие правки автоматически.
