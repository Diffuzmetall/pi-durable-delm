# Эксплуатация, диагностика и откат

Все команды ниже относятся к **вашему** пакету и RUN. Они не дают разрешения менять чужие сервисы или запускать дополнительные модели. Запуск команды агентов требует утверждённого плана и разрешённых участников; подготовка файлов сама по себе этого не разрешает.

## Первый запуск и правила

Читайте global/project AGENTS полностью по действительно разрешённым путям, включая применимые правила предков и подкаталогов. Нет файла или права чтения — сообщите это прямо, не выдавайте system injection за прочитанный файл. Установщик не должен создавать или переписывать глобальные правила.

Сохраните исходный утверждённый запрос, план и разрешённые references. Не экспортируйте по умолчанию всю прежнюю личную беседу. Каждый участник получает frozen WORKER, свой START и фактический первый input. Подготовленный prompt-файл и BOOT не доказывают принятие input Native или понимание плана.

До редактирования участник читает свежую доску: DONE с доказательствами, owners, blockers и оставшуюся работу. Названия задач формулируют на языке пользователя: действие + полезный результат. Отдельный этап или служебный UUID не заменяет понятного названия.

## Подключить к существующему Native

Установщик DeLM не устанавливает host и не регистрирует плагин автоматически (`native_registered:false`). Сначала проверьте у владельца вашего Native: session-facet loader, локальный `DurableSession` API 1 и публичный клиент протокола 1. Проверенный вариант — Native v1.0.2 с явной отдельной трёхфайловой API-поправкой; неизменённая stock-версия не подтверждена. [Контракт](native-compatibility.md), [установленная приёмка](user-host-acceptance.md).

Добавьте каталог DeLM payload к **существующему набору** plugins/default session profile средствами вашего Native. Публичный выбранный loader принимает package через `server -e PACKAGE`; это форма настройки уже имеющегося Native, не инструкция установить или собрать новый server. Не копируйте эту строку как имя несуществующего бинарника. Для уже запущенного host используйте его штатный выбор плагинов новых сессий. Не заменяйте прочие plugins списком из одного DeLM и не меняйте чужие активные сессии. `Run.py start` наследует выбранный owner profile (`packagePaths:null`), а не исправляет его сам.

Для скилла используйте стандартную project-local ссылку **до создания workers**:

```bash
mkdir -p "$PROJECT/.pi/skills"
python3 -c 'import sys; from pathlib import Path; Path(sys.argv[2]).symlink_to(sys.argv[1], target_is_directory=True)' \
  "$PACKAGE/skills/delm" "$PROJECT/.pi/skills/delm"
```

`Path.symlink_to` атомарно отказывает с `FileExistsError` при любой существующей записи назначения: файл, каталог, рабочая или dangling symlink остаются нетронутыми. Команда не создаёт вложенную ссылку в чужом каталоге. При отказе сначала разберитесь, чей это скилл. Ссылка не подключает session facet, а `pi.skills` в manifest не подтверждает Native discovery. Native кэширует список skills в worker: если он уже загружен, используйте поддержанный lifecycle новых сессий, не отправляйте dummy input для «обновления». Реальный prompt discovery проверен отдельно.

После `prepare` и запуска backend:

```bash
python3 "$PACKAGE/skills/delm/Tools/Run.py" start --run-dir "$RUN" --socket "$NATIVE_SOCKET"
python3 "$PACKAGE/skills/delm/Tools/Run.py" status --run-dir "$RUN"
python3 "$PACKAGE/skills/delm/Tools/Run.py" resume --run-dir "$RUN"
python3 "$PACKAGE/skills/delm/Tools/Run.py" stop --run-dir "$RUN"
```

`NATIVE_SOCKET` — точный Unix socket вашего уже работающего Native; автоматического поиска, запуска host и переключения на Pocket нет. Для обычного клиента source checkout не требуется. В тестах публичные зависимости предоставлялись внешними read-only resolvers без установки; это условие тестовой среды, не команда пользователя. Обычная среда должна разрешать объявленные публичные peers штатно.

## Backend, observer и участники

Из корня установленного пакета, после задания `RUN` путём вашего запуска:

```bash
python3 scripts/delm_local.py serve "$RUN"
```

Это foreground backend доски. Оставьте его работающим. В другом терминале из того же корня:

```bash
python3 scripts/delm_board.py "$RUN" --observe
```

Observer не владеет backend; `q`/Ctrl+C закрывает только просмотр. `--once` печатает один read-only снимок без сервера. Режим **без** `--observe`/`--once` — legacy объединённый server+observer, который останавливает свой backend при выходе; не открывайте его поверх действующего сервера.

Участники Native — отдельные процессы, не несколько серверов одной доски. Закрытие окна не завершает задачу и не публикует producer-ended. Tern нужен для автоматических панелей, но Python backend, CLI и observer не требуют его установки.

## Клавиши observer

- `Tab` — переключение задач/событий; `/` — поиск.
- Стрелки, `j`/`k`, PageUp/PageDown, Home/End — навигация.
- `Enter` — полные детали: UUID, исходный subject/detail, результат и история; `Esc` — назад.
- `f` — фильтр состояния, `a` — фильтр участника, `l` — фокус журнала.
- `q` — выход из observer без остановки отдельного backend.

Display key стабилен в пределах одного RUN и строится по первому появлению задачи, до сортировки. Это только подпись интерфейса; API принимает UUID. На узком экране дополнительные колонки могут скрываться, но детали остаются доступны. Выделение/копирование текста принадлежит терминалу. Просмотр старого журнала временно останавливает auto-follow; возврат к концу или пауза возвращает LIVE.

## Продолжение и изменение задания

Используйте сохранённую точную session identity и тот же RUN. Общий `--continue` по shared cwd может выбрать беседу другого участника. Не повторяйте старт после неопределённой доставки: сначала сверяйте прежний request/marker и accepted input, иначе получится второй запуск.

Новый комментарий, ответ на вопрос и разрешение на действие — разные вещи. Изменение задания передают через поддержанный Native control с сохранением нового исходного текста; не приписывают ему разрешение на расходы, публикацию или дополнительные модели. Если публичный control API отсутствует, это ограничение, а не повод подключить приватный host или другой orchestration runtime.

Перед reopening/reload сохраните несданный editor draft штатным способом. Не отправляйте его для проверки и не используйте dummy input, который случайно запустит модель. После восстановления проверьте точную беседу, draft и pending deliveries.

## Безопасная остановка

1. Прекратите новые мутации и разберите незавершённые claims, checkpoints и writers. Выполните `Run.py stop --run-dir "$RUN"` у совместимого host: он останавливает собственные watchers, затем abort/waitForIdle каждой точной беседы. Дождитесь подтверждения; закрытое окно не доказывает остановку фонового shell. Проверяйте внешние процессы отдельно.
2. Отдельно закройте observer. Это не остановит участников или backend.
3. Для foreground backend используйте Ctrl+C и дождитесь выхода. Для detached-процесса сначала сверяйте точный PID, argv и RUN по своей launch-записи и `ps`; сигнал посылают только этому процессу. Не используйте `pkill python`, `killall node`, удаление lock-файла или автоматический SIGKILL.
4. Проверьте, что процесс вышел и endpoint недоступен. Сам файл endpoint после неграциозного выхода может остаться.

`delm_wait cancel` и `Run.py stop` различаются: cancel отказывает после committed/accepted input; stop может прервать уже начатую генерацию, **не отменяя факт принятия** и не подтверждая чтение snapshot. Непрочитанный receipt остаётся pending. Реально проверены stop ожидающего watcher и stop начавшейся генерации при удержанном ответе модели; это не обещание принудительно уничтожить произвольный внешний shell-процесс.

Этот пакет не обещает универсальный group-stop для любого Native host. Неподдерживаемый stop должен дать явную ошибку; нельзя объявить run остановленным, оставив writers работать. Partial, blocked и stopped — не complete. Не показывайте ссылку на уже остановленный preview как действующую.

Для backend-продолжения повторите `serve` **того же RUN**, не `init`: история, tasks и receipts сохраняются. После восстановления транспорта failed Native delivery восстанавливают через штатный retry с исходным ID.

## Backup

Остановите новые записи и дождитесь завершения текущих операций. Для доски используйте SQLite backup API для **context и bodies** либо копию обоих файлов после подтверждённого закрытия backend. Не копируйте одну живую SQLite без учёта WAL и attached bodies.

Native backup и lifecycle выполняют штатными средствами host. Не открывайте session вторым владельцем и не редактируйте Native SQL. Сохраните также точные session identities, frozen инструкции, launch metadata и несданные drafts. Backup с token/config должен оставаться приватным.

Проверьте восстановление на disposable копии: события, вложения, курсоры, receipts и прежние waits должны остаться. Восстановление старого backup поверх более новой работы теряет историю; это отдельное решение владельца, не обычный rollback кода. Сохранённый pane ID не возвращает закрытую панель к жизни.

## Update и rollback

Установщик вправе менять только свои управляемые файлы/регистрации. Перед обновлением сохраните старый artifact, список файлов и hashes; сверяйте текущие hashes с ожидаемыми. Пользовательские изменения не перезаписывают ради «чистой» установки. Uninstall оставляет RUN, вложения, Native sessions и чужие файлы. Удаление данных требует отдельного разрешения.

**Особая граница work → старая версия:**

1. В версии с work проверьте status каждого участника.
2. Waiting/failed work-watchers штатно отмените или восстановите через retry/reconciliation до sent. Если cancel отказал из-за committed/accepted input, восстановите именно его; не стирайте запись.
3. Прочитайте pending snapshots и явно ACK. Убедитесь, что active/failed work-watchers не осталось. Исторические sent/cancelled записи сохраняйте.
4. Сохраните актуальные board+bodies, Native state, точные session paths и drafts. Дождитесь idle.
5. Только затем верните согласованный artifact и выполните поддержанный host reload в тех же сессиях. Frozen START/WORKER не подменяйте тайно; сообщите, что старый API не имеет work.
6. Проверьте загруженную версию, сохранение истории, прежние exact waits и отсутствие повторного input.

Старая версия может истолковать work с пустым items как «все зависимости DONE». Само совпадение версий SDK не делает downgrade безопасным. Нельзя компенсировать проблему очисткой SQLite или guards.

## Отключить и удалить только DeLM

Сначала подтвердите stop каждой точной сессии. Затем средствами **владельца Native** исключите только DeLM из plugin selection этих уже неактивных сессий, сохранив прочие plugins/guards. Выбранный публичный owner API `prepareSession({sessionId,packagePaths:[...сохранённые остальные...]})` отказывает при несовместимой смене активного worker; не обходите это редактированием SQL. Его высокоуровневый клиент возвращает presentation data, не список `packagePaths`.

Уберите только project-local skill symlink, который создавали сами: сначала проверьте точный target, не удаляйте существующий пользовательский каталог. После backup и подтверждённого отсутствия активных writers выполните payload `uninstall` сохранённым bootstrap. Он не удаляет проект, RUN, беседы, Native, его credentials или settings. Изменённые/дополненные version trees перечисляются в `retained`; не стирайте их автоматически. Старые actor CLI ссылаются на пакет и без его файлов не обязаны работать; сохранённую доску можно открыть после повторной установки, а не через подмену путей.

В приёмке чистое управляемое дерево удалено физически; те же Native session IDs сохранили обе истории, общий результат и оба файла доски, прежний guard продолжил работать, обычный Native prompt выполнился уже без DeLM tool/skill. Повторная установка того же payload вернула совместимую интеграцию без новых бесед. Это не удаление или откат пользовательских данных.

## Типичные проблемы

| Симптом | Что проверить |
|---|---|
| Второй backend не запускается | Уже действующий владелец `server.lock`; не удалять lock вслепую |
| `STALE` при task mutation | Свежую revision/generation, owner и checkpoint; не обходить fence |
| Не приходит READY | Все точные UUID DONE? Нет связанного FAIL? Producer действительно ended или лишь idle? |
| Work hint исчез | Другой участник мог выиграть claim; hint не назначает задачу |
| Receipt остаётся pending | Reference доставлен, но полное тело ещё не прочитано/ACK |
| Native integration недоступна | Проверенный публичный admission/control API, а не один номер SDK |
| Не открываются панели | Наличие Tern; отсутствие UI не означает потерю Python-доски |
| После source update поведение старое | Загруженный build отличается от файла на диске; нужен поддержанный idle reload |
| После downgrade ложный wake | Не были дренированы work-watchers; не редактировать хранилище для сокрытия |

## Безопасный bug report

Укажите версии Python/Node/Native, OS, версию и hash artifact, точную команду, exit code и минимальный пример на фиктивном проекте. Различайте source review, реальный HTTP, SDK/faux и живую модель. Приложите только очищенный traceback и небольшой релевантный фрагмент лога.

Не прикладывайте config/token/auth/provider settings, реальные conversation dumps, Native SQLite, RUN целиком, traces и скриншоты с личными данными. Task titles, workspace paths и публикации тоже могут быть приватными: перед пересылкой просмотрите их вручную. ACK чтения не является доказательством успешного теста кода.
